## Vault Guide: Handling Entity Creation Requests

The Vault is responsible for securely registering new entities and verifying client ownership of phone numbers. 
An **entity** represents a user identity within the Vault system.

This process involves:

1. Receiving entity creation requests from clients
2. Verifying phone number ownership via OTP
3. Completing entity creation with secure token and key exchange

---

### Step 1: Handle Initiate Creation Request

Upon receiving the initial `CreateEntityRequest`, the Vault must:

- Verify the phone number format
- Trigger OTP delivery to the user via SMS
- Store a pending entity entry with public keys and temporary data
- Respond with OTP status and next retry time

#### Request

```proto
message CreateEntityRequest {
  string phone_number = 1;
  string country_code = 2;
  string password = 3;
  string client_publish_pub_key = 4;
  string client_device_id_pub_key = 5;
}
```

#### 📤 Vault Actions

- Generate and send OTP to phone_number
- Store request in a temporary entity pool
- Set retry window and expiration

#### ✅ Response (CreateEntityResponse)

```json
message CreateEntityResponse {
  bool requires_ownership_proof = 1;
  string message = 2;
  int32 next_attempt_timestamp = 3;
}
```

---

### 🧾 Step 2: Handle Complete Entity Creation

After the client proves phone ownership (via OTP), the Vault receives another `CreateEntityRequest` — this time with the `ownership_proof_response` field.

#### 📨 Request Fields

In addition to initial fields, the following is now included:

```json
message CreateEntityRequest {
  string phone_number = 1;
  string country_code = 2;
  string password = 3;
  string ownership_proof_response = 4;
  string client_publish_pub_key = 5;
  string client_device_id_pub_key = 6;
}
```

#### 🔐 Vault Actions

- Validate OTP with stored proof
- If valid:
    - Generate and store a new entity record
    - Issue a long-lived token (JWT or similar)
    - Generate and return Vault’s server public keys
- If invalid:
    - Return error and throttle retries

#### ✅ Final Response (CreateEntityResponse)

```json
message CreateEntityResponse {
  string message = 1;
  string server_publish_pub_key = 2;
  string server_device_id_pub_key = 3;
  string long_lived_token = 4;
}
```

#### 🔁 Sample Successful Response

```json
{
  "message": "Entity created successfully",
  "serverPublishPubKey": "VAULT_X25519_PUB_KEY",
  "serverDeviceIdPubKey": "VAULT_DEVICE_ID_KEY",
  "longLivedToken": "vault_token_string"
}
```

---

### 📌 Vault Requirements

- Store encrypted passwords and tokens (e.g., using bcrypt + AES)
- Enforce OTP expiration and retry limits
- Ensure `long_lived_token` is securely generated (e.g., HMAC or JWT)
- Prevent duplicate entities for the same `phone_number`

### 🧪 Testing via CLI (grpcurl)

```json
grpcurl -plaintext \
  -d @ \
  -proto protos/v1/vault.proto \
  localhost:6000 vault.v1.Entity/CreateEntity < payload.json
```

### 🛡️ Security Notes

- OTPs should be single-use and time-limited (e.g., 5 minutes)
- All keys must use X25519 and be base64-encoded
- Long-lived tokens must be scoped and revocable
- Avoid storing raw OTPs — use a hash with timestamp
